## Comments

- 2026-11-06: Built in `dapp/packages/extension/`. Ticket 02 recorded Kohaku as failed, so this extension is the host that carries the Helios plus Anon-RPC trust level. The first box stays open until the light clients and the worker have booted in a real Chrome. The code is written and bundles, but nothing in it has run in a browser yet.
  - Files. `static/manifest.json`, `static/offscreen.html`, `static/anon-boot.html`, `build.mjs`, `package.json`, `tsconfig.json`. In `src/`: `page.ts` is the proxy and `page-entry.ts` its page-world entry. `bridge.ts` is the isolated-world content script. `overlay.ts` draws the overlay and `report.ts` holds the report type and the per-verdict plan. `targets.ts` unpacks each held method and passes it to the Snap's `decode.ts`, imported by relative path. `engine.ts` wires the reader. `offscreen.ts` boots Helios plus Anon-RPC. `background.ts` is the service worker. `anon-harness.ts` wraps the harness worker, and `chrome.d.ts` declares the few chrome APIs used. Tests are in `test/`.
  - Where the reader runs. In an offscreen document, not in the service worker. `@anon-rpc/browser-harness` 0.4.0 builds a sandboxed iframe with `document.createElement` and starts a `Worker` inside it. Service workers have no `document` and no `Worker` constructor, so the harness cannot start there. The service worker creates the offscreen document on install, on browser start, and on the first held request (reasons `WORKERS`, `IFRAME_SCRIPTING`, `WEB_RTC`). It relays each request to that document and keeps the pin and checkpoints in `chrome.storage.local`, because an offscreen document gets only `chrome.runtime`.
  - Harness use. `offscreen.ts` imports `startHelios`, `bootstrapAnonRpc` and `installFetchShim` from `dapp/packages/nextjs/utils/harness/anonHelios.ts` without changing them. The log address comes from its `LOG_ADDRESS`. The flow matches the harness page. It boots mainnet Helios, uses that to boot the worker, shuts mainnet Helios down, shims the Sepolia execution URL through `worker.fetch`, then starts Sepolia Helios. One snag: by default the harness writes its boot script inline into an iframe `srcdoc`, and an extension page's CSP blocks inline scripts. The harness also reads an `iframeUrl` option that loads the same boot script from a same-origin page. That option is in `dist/host.js` but missing from its types. `build.mjs` points every import of the package at `src/anon-harness.ts`, a subclass that adds `iframeUrl: anon-boot.html`. That page is a manifest sandbox page, so it has an opaque origin and a CSP that allows the harness's blob worker. If `bootstrapAnonRpc` took an optional `iframeUrl`, the build plugin could go.
  - Transports. Header, storage proofs, ENS and list record go through Sepolia Helios. That is the reader's `rpcProofSource` over Helios with `unverified` dropped, since Helios checks the header and the proof. A "latest" read that Helios refuses as out of sync falls back to "finalized". Leaves come from `eth_getLogs` to the Sepolia execution URL, and the fetch shim sends those through the worker too. The list document at `listURI` is fetched directly, not through the worker. `TOCSIN_TRANSPORT=direct` skips the worker and mainnet Helios, and the overlay then says "direct to the RPC, not anonymised". Use it as the venue-wifi fallback if Tor and Nym are blocked. Sync runs at boot and every five minutes.
  - Proxy. `world: "MAIN"` content script at `document_start`, so no `<script>` tag is injected and the page's CSP does not apply to it. `window.ethereum` becomes a configurable accessor, so a wallet that assigns it later is still wrapped, and a wallet that redefines it is not blocked. EIP-6963 announcements are caught in the capture phase, stopped, and re-announced with the wrapped provider. Every property except `request` is read from the real provider, and methods are bound to it, because wallets keep private fields. A held request first reads `eth_chainId` through the real wallet, then waits for the bridge's answer. No rejects with EIP-1193 code 4001 and the wallet never sees the request. Held requests run one at a time.
  - Checks per method. `eth_sendTransaction`: `to`, plus the decoded transfer recipient, approve/permit spender or operator, all using the Snap's rules. `eth_signTypedData_v4`: the spender of an EIP-2612 or Permit2 permit, on the chain in the domain. `wallet_sendCalls`: every call, deduplicated, on the batch's `chainId`. A request with no address to check gets no overlay. The worst verdict across all targets decides.
  - Overlay. A closed shadow root, styled through a constructed stylesheet so the page's `style-src` does not block it. Light and dark tokens, `role="alertdialog"`, focus kept on its two buttons, Escape stops. `block`: "Stop this request" is primary, and "Override and open wallet" counts down 5 seconds before it enables. `warn`: "Continue to wallet" works at once. `unavailable`: states the reason (still starting and at which step, startup failed, no list, the engine did not answer) and offers Continue. For each finding it shows the writer (forward-checked ENS name or a short address), the category name, and the evidence linked to `sepolia.etherscan.io/tx/`. Then the sync block, how the header was verified, the transport, the list name with maintainer and version, and the ERC framing: "The chain proves each flag is the writer's own entry, complete and in order. Whether the writer is right is your pinned list speaking." If the overlay cannot render, the request is stopped, not let through.
  - What happens to the request. The page and the bridge pass it over `window.postMessage` to the page's own origin, and the bridge passes it to the service worker and the offscreen document over `chrome.runtime` messaging, all in memory. Nothing writes it to storage, logs it, or sends it off the device. `chrome.storage.local` holds only the pinned list and the checkpoints. There is no `console` call in `src/`.
  - Build. `node dapp/packages/extension/build.mjs` uses the esbuild 0.27.0 under `packages/nextjs/node_modules`, where Helios, the harness and its viem also live. No dependency was added and nothing was installed. Settings are read at build time from the shell, then from `packages/nextjs/.env.local` (the harness page's file): `NEXT_PUBLIC_HARNESS_SEPOLIA_CONSENSUS_RPC`, `NEXT_PUBLIC_HARNESS_SEPOLIA_EXECUTION_RPC`, `NEXT_PUBLIC_HARNESS_MAINNET_CONSENSUS_RPC`, `NEXT_PUBLIC_HARNESS_MAINNET_EXECUTION_RPC`, `NEXT_PUBLIC_HARNESS_TOR_GATEWAYS`, plus `TOCSIN_TRANSPORT` (tor, nym or direct, default tor), `TOCSIN_LIST_NAME`, `TOCSIN_LIST_RECORD`, and `TOCSIN_LOG_FROM_BLOCK`. A keyed RPC URL ends up in `dist/`, which is git-ignored. Output: `offscreen.js` is 5.1 MB (mostly Helios's inlined wasm), `page.js` 3 KB, `bridge.js` 8 KB, `background.js` 2 KB.
  - Checked locally. `tsc --noEmit -p dapp/packages/extension` (the Snap's tsc 5.8.3) passes. It also checks the reader, the harness module and `decode.ts` through their imports. `node --test test/*.test.ts` passes 19 tests. `page.test.ts` covers the intercept list against eleven other methods, pass-through without asking, release after a yes with the wallet's chain id, 4001 on a no with the wallet never seeing the request, bound methods on a wallet with private fields, `window.ethereum` assigned before and after the proxy, and EIP-6963 re-announcement. `report.test.ts` covers the plan for each verdict and the override delay. `targets.test.ts` covers the three methods and malformed page params. `bundle.test.ts` loads the built `dist/page.js` in a fresh `node:vm` context with a fake `window.ethereum` and a fake bridge. It covers a pass-through that never posts, a held send released on yes, a 4001 on no, and a reply with the wrong id that does not release the request.
