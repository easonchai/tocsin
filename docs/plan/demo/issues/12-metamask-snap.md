## Comments

- 2026-11-06: Built in `dapp/packages/snap/`. Ticket 02 made the Snap the primary host, so the three beats run here.
  - Files. `snap.manifest.json` and `snap.config.ts`, plus `images/icon.svg` and `tsconfig.json`. In `src/`: `decode.ts` picks which address gets checked and in which context, `engine.ts` wires the reader to the Snap, `state.ts` holds Snap state and the bigint codec, `settings.ts` validates the settings form, `ui.tsx` has the panel, the settings page and the maintainer dialog, and `index.tsx` exports the handlers. In `test/`: `decode.test.ts` and `bundle.test.ts`. `package.json` gained `"type": "module"`, `files`, and a `test` script.
  - Permissions: the spec's six (`endowment:transaction-insight` and `endowment:signature-insight`, both with origin, plus `endowment:cronjob`, `endowment:network-access`, `snap_manageState`, `snap_dialog`) and two more. `endowment:lifecycle-hooks` is the only way `onInstall` runs, and without it there is no sync on install. `endowment:page-settings` is the only way `onSettingsPage` runs, and the source switch, RPC, and list name live there. No `endowment:ethereum-provider`: the Snap never reads through MetaMask's RPC, only its own configured one.
  - Decoding. `to` is checked as recipient. The spender context covers ERC-20 `approve`, `setApprovalForAll` (operator), an EIP-2612 `permit` sent as a transaction, Permit2 `approve(token, spender, ...)`, and both Permit2 `permit` overloads (single and batch). ERC-20 `transfer` adds its recipient. `onSignature` handles `eth_signTypedData_v3/v4`, whether the data arrives as an object or a JSON string. For primary type `Permit` and the Permit2 permit types it checks `message.spender`, and it takes the chain from `domain.chainId`. Any other signature gets no panel at all. Unknown calldata adds nothing beyond `to`. `transferFrom` and `increaseAllowance` are not decoded.
  - Lists. The list name defaults to the build-time `TOCSIN_LIST_NAME` and can be changed in settings. The Snap reads `erc-threat-flag-log.list` through the reader's `resolveListRecord`, which sends one `eth_call` to the configured RPC with CCIP-read off. It then fetches the record's `listURI` and runs `acceptList` against the pin held in state. A conflict opens a `snap_dialog` confirmation with the old and new maintainer and version. Yes pins the candidate. No keeps the pin and stores the candidate's root, so that same list is not asked about again on every cron tick, and the settings page shows "declined". Changing the list name in settings starts a fresh pin, because the ERC pins per name. `TOCSIN_LIST_RECORD` at build time replaces the ENS lookup for a rehearsal before the name exists (one line in `fetchList`). Writer names come from `reverseName` at sync time. A writer without a forward-checked name shows as `0x1234…abcd`.
  - Sync. Runs on install, on the cron job (`*/5 * * * *`), and on Save or Sync now in settings. Before anything else it checks that the RPC answers `eth_chainId` 11155111. Proofs come from `rpcProofSource` over the configured RPC, default `https://ethereum-sepolia-rpc.publicnode.com`. Leaves come from the leaf source switch: rpc (the same RPC), custom URL (default `http://127.0.0.1:8550`, the lying proxy), or snapshot (each entry's `snapshotURI`). Switching the source, the RPC, or the from-block clears the checkpoints. Otherwise a checkpoint taken from the honest source would hide the proxy's lie in beat 2. Snap state is the default encrypted store. Bigints are stored as `{"$n": "<decimal>"}` and Errors as their message. A failed sync keeps the previous result, and the panel says so.
  - Panel. A Banner per verdict. `block` returns `severity: "critical"`, the only severity snaps-sdk 12.1.0 has. `warn` and `unavailable` get a warning Banner with no severity. For each finding the panel shows the writer, the category name, and the evidence linked to `sepolia.etherscan.io/tx/`, with a tooltip saying it may be a bundle hash. An `unavailable` writer is shown with "chain mismatch at sequence N" or the source error. The footer gives the sync block, the leaf source, and "Header from <host>, unverified", then the best-effort sentence ("the RPC is not anonymised"), then the ERC framing. The Snap makes no Anon-RPC claim. `clean` comes from the reader's `evaluate`, which returns `unavailable` unless every pinned writer synced.
  - Checked locally. `yarn workspace @tocsin/snap check-types` passes, and tsc also checks the reader source it imports. `yarn workspace @tocsin/snap build` compiles 320 files and reports "Snap bundle evaluated successfully" (SES), with one warning: package.json has no `repository`. `yarn workspace @tocsin/snap test` builds and then runs 28 `node:test` tests, all passing. Fourteen cover decoding and the settings form. The other fourteen load `dist/bundle.js` with a fake `snap` global and a fake `fetch`. They cover the pre-list "not synced" panel, all three beats, a permit block at signing, an `approve` block, the shortened detector address, the maintainer dialog (no, not asked again, then yes), a wrong-chain RPC, bigints surviving the JSON store, and settings field errors. Fixtures are built with the reader's own `chain.ts` and `lists/index.ts`. `mm-snap serve` on port 8080 served the manifest, the 240 KB bundle, and the icon. Live, `ethereum-sepolia-rpc.publicnode.com` answered `eth_getProof`, the `finalized` tag, and a 10,000-block `eth_getLogs`, all with `access-control-allow-origin: *`.
  - Test runner. Vitest is not resolvable from this package (`nmHoistingLimits: workspaces` keeps it in reader's and infra's `node_modules`), and `@metamask/snaps-jest` is not installed. The tests use Node 26's built-in runner with type stripping. No dependency was added.
  - Not verified, needs a browser: everything inside MetaMask. That covers the install, the real insight rendering and critical-severity styling, the cron firing, dialogs from the cron context, encrypted state while the wallet is locked, and whether the Snap's fetch can reach `http://127.0.0.1:8550`. On the last one, Chrome's local network access rules may block a request from the Snap's iframe to localhost. If they do, put the proxy behind an https tunnel and enter that URL as the custom leaf URL.
  - Open. The log is not deployed and the team's name is not registered, so the defaults have nothing to read yet. Build with `TOCSIN_LOG_FROM_BLOCK` set to the deployment block.
